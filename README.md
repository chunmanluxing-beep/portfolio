# 产品作品集 · 静态站

一个产品经理作品集单页,介绍「榴档期 · 旅拍自动化调度管理系统」这套真实运行的生产系统——它给谁用、两个端怎么分工、一条订单怎么走完、以及这套系统是怎么交付出来的。

## 这是什么

我在日本做旅拍业务,自建了一套覆盖「接单 → 建单 → 派单 → 拍摄 → 交付 → 结算」全链路的业务系统,由三个端协同:运营总控台(管理端)、摄影师移动端「榴档期 App」(iOS 已上架 App Store)、客人免登录交付页。

站点按**先总后分**组织:

- 先说给谁用(四类使用者),再说系统由哪两个入口构成
- 用一张「一条订单的完整旅程」把全站串起来,**七步全部是可点目录**,点哪一步就跳到讲它的那一章
- 能力按**双主线**编排:屏 3「运营总控台」四块(建单 / 派单 / 交付 / 结算)、
  屏 4「榴档期 App」四块(档期 / 抢单 / 预警 / 收入),每一块都是主线上的一段
- 密度控制:深论证收进 `<details>`,默认折叠但一条没删

## 如何替换截图占位

页面里预留了 **36 处**真实截图占位区(虚线框),去重后需要 **32 张主图**(其中 23 张已到位、9 张待重截/待补)。

> **完整清单见 [`images/README.md`](images/README.md)** ——每一处占位对应哪个文件名、放什么截图、在哪一屏、建议尺寸、必须打码什么,都列好了,并按优先级分组列出。页面上每个占位框的第二行也直接写着它对应的文件名。

### 放图即显示(不需要改任何代码)

页面里 36 处占位已经全部预接好 `<img>`:先找 `.png`,找不到自动找同名 `.jpg`,两种都没有才回落成虚线占位框。

1. **先打码**——客人姓名、电话、邮箱、金额、订单号、网盘提取码等敏感信息必须处理干净再入库。图片一旦提交进 Git 并推上 GitHub,历史里就永远存在,删掉当前版本也没用。
2. 照着 [`images/README.md`](images/README.md) 的文件名(全小写、连字符、`.png`),把图放进 `images/`。
3. 刷新页面——**放进去就显示了,`index.html` 一行都不用改**。
4. 想让它出现在线上,`git add images/xxx.png` 后提交推送即可。

回落机制(每处占位的实际结构):

```html
<figure class="shotwrap">
  <input type="checkbox" id="lb-N" class="lb-toggle">          <!-- 灯箱开关(纯 CSS) -->
  <label class="lb-zoom" for="lb-N">
    <img class="shotimg" src="images/console-orders-list.png" alt="总控台订单列表页"
         onerror="…先试同名 .jpg,再隐藏并显示占位框…">
    <span class="lb-tip">⤢ 点击放大</span>
  </label>
  <div class="shot">…占位框…</div>
  <div class="lb-overlay">                                     <!-- 点击后的全屏大图 -->
    <label class="lb-close" for="lb-N">✕</label>
    <label class="lb-back" for="lb-N"><img src="同一文件" loading="lazy"></label>
  </div>
</figure>
```

- `.shotwrap > .shot` 在 CSS 里默认 `display:none`,只有 `onerror` 触发时才置回 `flex`
- 图片加载失败时缩略区自动隐藏,**不会出现浏览器默认的破图图标**,占位框也不会带灯箱
- **每张已显示的截图都可点击放大**:`checkbox:checked ~ .lb-overlay` 全屏呈现同一文件(缓存命中,零额外流量),点暗底任意处或右上角 ✕ 关闭
- 卡片内的 31 处用 `.shotwrap-in`,图片最大高度 420px;主线 5 处 520px

占位框不替换也不影响观感——它本身是按设计元素处理的,留着即可。

## v15.0 新增:竖图容器 / 多图轮播 / 手机端适配

### 一、竖图专用容器 `.shot-portrait`

摄影师端(App)截图是 **780×1688 手机竖图**,塞进按横图设计的 `width:100%` 容器里
会被 `object-fit:contain` 压成「宽框里的一根细条」,两侧留大片空底。v15 给这 10 处
(9 处已有图 + 1 处 B 类占位 `app-urgent-push`)加了 `shot-portrait` 类:

- 图片按自然比例收窄居中:桌面 `max-width:300px`、`max-height:640px`;窄屏 `min(300px,78vw)` + `max-height:72vh`
- 圆角 18px + 1px 浅边 + 投影,做出手机壳观感
- **无图态占位框同步改成竖比例虚线框(9:19.5)**,不再「横框等竖图」
- 灯箱内竖图:高度上限仍是 92vh,宽度按 780:1688 反推封顶(`min(94vw,44vh)`),不会出现超宽拉伸

### 二、多图轮播 `.shotdeck`(一个占位挂多张分截图)

**文件名约定**:主图 `<名>.png|.jpg`,追加图 `<名>-2` / `<名>-3` / `<名>-4`,**最多 4 张**。
把分开截的几张按这个序号丢进 `images/` 即可,不需要改 HTML。

- 纯 CSS:每张图对应一个隐藏 `input[type=radio]`(`name` 按占位唯一分组)+ 图下圆点 `label` 行,`:checked` 决定显示哪张
- **渐进增强**:圆点行默认隐藏,只有第 2 张真的加载成功(`onload` 打上 `.deck-multi`)才出现——
  只有主图时零圆点,外观与 v14 逐像素一致
- 圆点:视觉 8px(当前页琥珀实心、其余描边),触控热区 44×44
- **灯箱联动**:radio 与 `.lb-overlay` 同为 `figure` 直接子元素,用 `~` 共享 `:checked` 状态,
  放大看到的就是当前选中的那一张,不需要任何脚本
- v15 已为 4 处已知会有多张的占位预置了 2 图结构:`guest-photo-select`(×2 处)、`guest-delivery-page`(×2 处);
  其余 33 处保持单图结构不动

### 三、B2 撤销

「新版本更新提示」那一处占位整块删除(占位数 38 → 37),对应文件名一并从两份清单里摘除。
「版本自动感知」这块能力本身**保留、文字一字未动**——能力是真的,只是不配图。

### 四、手机端适配(第一验证视口 390×844)

- 触控热区:顶部导航 41×25 → 45×47;「统计口径」summary 39 → 44;
  正文内联链接(App Store 外链 / 「详细 →」/ 「专章 →」/ 邮箱)用不可见 `::after` 扩到 44px(版式一字不动);
  灯箱关闭键 40 → 46,并把 padding 从 overlay 挪进 `.lb-back`,使「点暗底任意处即关」覆盖到边缘
- 灯箱大图 `max-height` 加 `dvh` 兜底(`92vh` → `92dvh`),手机地址栏收起/展开不再错位裁切
- **新增 480px 断点**:v14 的单列断点停在 380px,而 390 是最常见的 iPhone 逻辑宽度——
  `.stats` 在 390 仍是两列(卡内截图被压到 90px 宽)、`.kpis` 在任何宽度都不塌成单列(116px 宽)。
  ≤480px 一律单列后,卡内截图回到 272–300px 宽

`#home` 英雄区逐行量 boundingBox,**1280 下发现品牌行整体偏左 32px**:

| 行 | 宽(改前 → 改后) | 中轴偏差(改前 → 改后) |
|---|---|---|
| 眉题 | 1024 → 1024 | +0 → +0 ✓ |
| logo | 112 → 112 | +0 → +0 ✓ |
| **品牌名 h1** | **960 → 1024** | **−32px → +0px** ✓ |
| **品牌副行** | **960 → 1024** | **−32px → +0px** ✓ |
| 定位句 | 1024 → 1024 | +0 → +0 ✓ |
| 提示句 | 1024 → 1024 | +0 → +0 ✓ |

**根因**:全局有一条 `h1 { max-width: 960px }`(给旧版左对齐大标题用的)。
`.hh-brand` 是 h1,容器内容宽 1024,它被限到 960 又没有 `margin:auto`,于是左锚定 ——
**中轴恰好偏左 (1024−960)/2 = 32px**。其余行都是块级满宽 + `text-align:center`,所以只有它错位。
390 下容器只有 354px、够不到 960 上限,所以**手机上看不出来,只有桌面能看出来** —— 这也是它一直没被发现的原因。
修法:`.hh-brand { max-width: none; margin-inline: auto; }`。

**390 单列下高度差 21.2px**(介绍句 1 行 / 2 行不等)。

## 一、侧栏滚动跟随:纯 CSS scroll-spy(零脚本)

用**滚动驱动动画**做的 scroll-spy:`html` 上 `timeline-scope` 声明 8 条命名时间线,
8 个 section 各自 `view-timeline-name`,侧栏 8 项分别绑定对应时间线。

两个关键取舍,都是被实测逼出来的:

**① 探测区缩成一条 1px 线。** 直接用 `animation-range: contain` 时,
相邻两章之间会空出**整整一个视口高度**没有任何高亮(章 A 的 contain 结束于
`A.bottom - vh`,章 B 才从 `B.top` 开始)。改成
`view-timeline-inset: 68px calc(100% - 69px)`,把探测区压成视口顶部 68px 处
(= 粘性导航高度 + 留白)的一条 **1px 线**——"当前章"就是这条线落在谁身上,
相邻两章首尾相接,**既不空档也不双亮**。

**② 不用 0%/100% 关灯的阶跃写法。** 起初写成 `0%{灭} 1%–99%{亮} 100%{灭}`,
结果章顶附近仍然不亮:`#console` 高约 11000px,**1% 就是 110px,30px 才占 0.27%**,
落在"灭"的那一格里。改成**区间内恒亮 + `animation-fill-mode: none`**——
区间外动画不生效,自然回落到基础灰样式,再没有精度问题。

**回退**:整套包在 `@supports (animation-timeline: view())` 内;
不支持的浏览器**完整回落到 v19 起就有的 `:target` 点击高亮**(那套一行没删),两套并存不冲突。

**reduced-motion 下保留**:scroll-spy 只改颜色与圆点填充,**不产生任何位移**,
不属于运动装饰,关掉反而会让人不知道自己在第几章。实测 reduce 下
`getAnimations()` 返回 16 条,归属清点为 `railOn ×8 + railDot ×8`,**全是这套颜色动画**,
其余装饰动画一条不剩。

> 共同约定:抢单口径一律排除软删(`go.deleted_at IS NULL`);窗口用 JST。
> 每条都先给「站上现值」,便于跑完直接比对。

```sql
-- ── ① 抢单成交率:站上现值 74.7% ──────────────────────────────
--    口径:被摄影师主动接走的抢单任务数 ÷ 已发起的抢单任务总数
--    待定项:分母是否剔除「已取消(cancelled)」与「中途改手动指派」的任务 —— 故一次把三种分母都算出来
SELECT
  SUM(status = 'grabbed')                                    AS 分子_已被抢走,
  COUNT(*)                                                   AS 分母A_全部已发起,
  SUM(status <> 'cancelled')                                 AS 分母B_剔除已取消,
  SUM(status IN ('grabbed','expired'))                       AS 分母C_仅抢走与超时,
  ROUND(100 * SUM(status='grabbed') / NULLIF(COUNT(*),0), 1)                 AS 率A_pct,
  ROUND(100 * SUM(status='grabbed') / NULLIF(SUM(status<>'cancelled'),0), 1) AS 率B_pct,
  ROUND(100 * SUM(status='grabbed') / NULLIF(SUM(status IN ('grabbed','expired')),0), 1) AS 率C_pct
FROM grab_offers
WHERE deleted_at IS NULL
  AND created_at >= '2026-05-01 00:00:00' AND created_at < '2026-09-01 00:00:00';

-- ── ② 接单时长中位数:站上现值 2.0 分钟 ────────────────────────
--    口径:每个成交任务的 (grabbed_at − created_at),对全部成交任务取中位数
--    待定项:统计窗口起止;循环再推的场次如何计入(本 SQL 按「发起时刻」锚,再推不重置)
SELECT
  COUNT(*) AS 成交任务数,
  ROUND(AVG(mins), 2) AS 均值_分钟_参考,
  ROUND(MAX(CASE WHEN rn <= (cnt + 1) DIV 2 THEN mins END), 2) AS 中位数_分钟
FROM (
  SELECT TIMESTAMPDIFF(SECOND, created_at, grabbed_at) / 60.0 AS mins,
         ROW_NUMBER() OVER (ORDER BY TIMESTAMPDIFF(SECOND, created_at, grabbed_at)) AS rn,
         COUNT(*)    OVER ()                                                        AS cnt
  FROM grab_offers
  WHERE deleted_at IS NULL AND status = 'grabbed' AND grabbed_at IS NOT NULL
    AND created_at >= '2026-05-01' AND created_at < '2026-09-01'
) t;

-- ── ③ 一次推送即成交:站上现值 96.0% ───────────────────────────
--    口径:首轮推送即成交的任务数 ÷ 成交任务数
--    实现:grab_candidates.notified_at 是「滚动时间戳」(循环再推会覆盖),
--          故「首轮即成交」= 抢到时刻早于任何一次再推(即该单候选的 notified_at 最大值 ≤ grabbed_at
--          且发起到抢到的间隔 < 一个再推周期 grab_repush_interval_min,默认 30 分钟)
--    待定项:分母取「成交任务」还是「全部已发起」;再推场次的界定 —— 两个分母都给
SELECT
  SUM(one_shot)                                              AS 分子_首轮即成交,
  COUNT(*)                                                   AS 分母A_成交任务,
  (SELECT COUNT(*) FROM grab_offers
    WHERE deleted_at IS NULL
      AND created_at >= '2026-05-01' AND created_at < '2026-09-01') AS 分母B_全部已发起,
  ROUND(100 * SUM(one_shot) / NULLIF(COUNT(*),0), 1)         AS 率A_pct
FROM (
  SELECT go.id,
         (TIMESTAMPDIFF(MINUTE, go.created_at, go.grabbed_at)
            < COALESCE((SELECT CAST(setting_value AS UNSIGNED) FROM system_settings
                         WHERE setting_key = 'grab_repush_interval_min'), 30)) AS one_shot
  FROM grab_offers go
  WHERE go.deleted_at IS NULL AND go.status = 'grabbed' AND go.grabbed_at IS NOT NULL
    AND go.created_at >= '2026-05-01' AND go.created_at < '2026-09-01'
) x;

-- ── ④ 抢单承接占比:站上现值 32.9%(上线后头两个月)────────────
--    口径:同期由抢单方式成交的派单数 ÷ 同期全部派单数(含手动指派)
--    待定项:窗口的精确起止日 —— 先把抢单功能首单日查出来,再据此定窗
SELECT MIN(created_at) AS 抢单功能首单日_据此定窗 FROM grab_offers WHERE deleted_at IS NULL;

--    定窗后跑这条(把两处 :start / :end 换成上面查到的首日与首日+2个月):
SELECT
  SUM(oi.id IN (SELECT item_id FROM grab_offers
                 WHERE deleted_at IS NULL AND status = 'grabbed'))          AS 分子_抢单成交派单数,
  COUNT(*)                                                                  AS 分母_全部派单数,
  ROUND(100 * SUM(oi.id IN (SELECT item_id FROM grab_offers
                 WHERE deleted_at IS NULL AND status = 'grabbed'))
            / NULLIF(COUNT(*),0), 1)                                        AS 承接占比_pct
FROM order_items oi
JOIN orders o ON o.id = oi.order_id AND o.deleted_at IS NULL
WHERE oi.deleted_at IS NULL
  AND oi.photographer_id IS NOT NULL          -- 已派出的行才算「派单」
  AND oi.created_at >= :start AND oi.created_at < :end;

-- ── ⑤ 累计处理订单:站上现值 481 笔 ────────────────────────────
--    口径:订单表中的订单记录总数,覆盖 OTA 与自营双渠道
--    待定项:是否包含已取消 / 已退款 —— orders.status 无「已取消」态(6 态见 init.sql),
--            故用 deleted_at 与 payment_status 分别切一刀,三个口径一起给
SELECT
  COUNT(*)                                                   AS 口径A_含软删全部,
  SUM(deleted_at IS NULL)                                    AS 口径B_排除软删,
  SUM(deleted_at IS NULL AND status = '已完结')               AS 口径C_仅已完结,
  SUM(deleted_at IS NULL AND channel = 'self')               AS 其中_自营,
  SUM(deleted_at IS NULL AND channel <> 'self')              AS 其中_OTA平台
FROM orders;

--    渠道分布(核对「双渠道」表述):
SELECT channel, COUNT(*) AS 单数 FROM orders WHERE deleted_at IS NULL
GROUP BY channel ORDER BY 单数 DESC;

-- ── ⑥ 覆盖城市与地区:站上现值 9 地 ────────────────────────────
--    口径:拍摄地点表中去重后的城市 / 地区数
--    待定项:是否含已停用地点(is_active = 0)—— 两个口径都给;
--            并列出实际城市名,核对站上那九项(京都/东京/大阪/奈良/福冈/镰仓/富士山/札幌/小樽)
SELECT
  COUNT(DISTINCT city)                                          AS 口径A_含停用,
  COUNT(DISTINCT CASE WHEN is_active = 1 THEN city END)         AS 口径B_仅启用
FROM meeting_points WHERE deleted_at IS NULL;

SELECT city, SUM(is_active = 1) AS 启用点位, COUNT(*) AS 全部点位
FROM meeting_points WHERE deleted_at IS NULL
GROUP BY city ORDER BY 全部点位 DESC;

--    交叉核对:实际有订单发生的拍摄地(orders.shoot_location 是自由文本,只作参照)
SELECT region, COUNT(*) AS 单数 FROM orders WHERE deleted_at IS NULL
GROUP BY region ORDER BY 单数 DESC;
```
